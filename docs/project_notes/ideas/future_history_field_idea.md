# Future-History Field Planning Idea

Date: 2026-03-24

## Core Idea

The current action chunk should not depend only on the current observation. Instead, it should be generated by reading from a latent context that contains both:

- historical evidence
- prospective future hypotheses

The readout should be query-based, so the current chunk can dynamically decide which parts of the past and future are most relevant.

## Main Points

### 1. Chunk generation should read both history and future

The current chunk is generated by querying a latent context with attention or an equivalent readout mechanism.

This context has two different semantic sources:

- history latents: what has already happened
- future latents: what may happen next under the current task and observation

So the chunk is not purely reactive. It is conditioned on both retrospective and prospective information.

### 2. History should preferably be stored as a continuous field

History should not grow forever as a raw token cache.

Instead, it is better to compress history into a continuous, queryable history field:

\[
H_t(\tau), \quad \tau \in [-T, 0]
\]

This has several intended benefits:

- bounded memory growth
- direct time-based access to the past
- better handling of different temporal scales
- cleaner support for query-based retrieval

The history field itself stores latents, not raw trajectories, but these latents should still be grounded in observation, state, and action streams during construction.

### 3. Future should also be represented as a field

Future should not be modeled only as a fixed list of planning tokens.

Instead, future should be represented as a prospective latent field conditioned on:

- the history field
- the current observation
- the long-horizon goal / instruction

\[
F_t(s), \quad s \in [0, T_f]
\]

From this future field, the model can read or sample local future latents for different horizons.

### 4. History is evidence, future is hypothesis

The historical field and future field have different roles:

- history field: stores evidence about what has actually happened
- future field: stores a predicted, revisable hypothesis about what may happen next

So the model should not treat them as identical token sources, even if both are implemented as latents.

### 5. The current chunk should query both fields

The current chunk query should read from:

- the history field, to retrieve relevant past evidence
- the future field, to retrieve relevant prospective constraints

This means the historical field and future field are not only storage structures. They are control-relevant latent memories.

## Recommended Interpretation

This framework can be understood as a closed-loop latent planning system:

1. compress past interaction into a history field
2. condition on history field, current observation, and long-horizon goal
3. generate a future field
4. let the current chunk query both fields
5. execute the chunk and update history
6. regenerate the future field at the next step

So planning is not a single fixed commitment. It is a revisable latent hypothesis conditioned on accumulated history.

## Important Clarifications

### A. Type labels alone are not enough

Simply adding a `history` or `future` embedding is not sufficient to define semantic meaning.

The difference between history and future should come from:

- different write/update rules
- different training objectives
- different system roles

Type embeddings can still help, but they are only auxiliary signals.

### B. Relative time is more important than manually fixed distance weights

Once latents carry relative temporal position, the model can learn by itself which past or future regions matter most.

So it is usually better to:

- provide relative temporal structure
- let attention learn importance

rather than manually forcing near-future tokens to always have larger weights.

### C. Storing only latent history can be acceptable

If the stored history latent is trained to behave as a sufficient control-relevant historical state, then the system does not need to keep replaying raw state/action sequences at inference time.

In that sense, the history field can be interpreted as a reusable control cache.

### D. Time-based query and content-based query are complementary

The history field provides a temporal coordinate system.

Attention provides relevance-based readout.

So:

- time organizes memory
- attention decides what to read

## Open Questions

- How should the history field be parameterized: spline, basis coefficients, neural field, or latent ODE/CDE style state?
- How should the future field be trained so that it captures planning structure rather than low-level action hints?
- How should historical evidence and future hypotheses be fused when producing the current chunk?
- Should future uncertainty be modeled by multiple future hypotheses or by one continuous future field with stochastic generation?

## One-Sentence Summary

The main proposal is to replace raw growing token memories with a queryable historical field and a generated prospective future field, so that the current action chunk is produced by jointly reading past evidence and future hypotheses in latent space.
